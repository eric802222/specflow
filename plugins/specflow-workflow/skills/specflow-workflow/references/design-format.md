# design.md / review.md 格式參考

`design.md`（工程決策）跟 `review.md`（code review 發現）共用同一套核心機制
（`lib/common/structured_decision.py`），只是欄位名稱換了。寫這兩種檔案之前
先讀這份，不要憑印象套用格式——這裡的規則會被 lint 嚴格檢查，寫錯格式會被
`specflow next` 擋下來。

## design.md

### 已定案（✅）

```markdown
### ✅ D1 — <一句話結論>

- **事件**：<觸發這個決策的情境／問題是什麼>
- **決策**：<選了什麼>
- **取捨**：<放棄了什麼、換來什麼代價（可省略此行）>
```

- 欄位順序固定：`事件` → `決策` → `取捨`
- `事件`、`決策` 必填，`取捨` 可省略
- 不能出現這三個欄位以外的任何文字（不準寫成自由段落）

### 待確認／卡住（⏳／🚫）

```markdown
### ⏳ D2 — <還沒定案的問題，一句話描述>

- **事件**：<觸發這個決策的情境／問題是什麼>
- **選項**：
  - [ ] <候選方案一>
  - [ ] <候選方案二>
  - [ ] 其他補充：
- **取捨**：<可選>
```

- **不能寫 `決策` 欄位**——還沒定案就不該假裝有答案
- `選項` 改用 checkbox 語法（跟 `tasks.md` 同語法），**至少 2 個候選方案**，
  且**必須包含一項「其他補充：」**，避免變成強迫二選一
- 勾了一個選項、但狀態還是 `⏳`／`🚫`，會被 lint 擋下——代表已經決定了，
  該把這個決策改成 `✅`、改用「事件／決策／取捨」欄位記錄最終結果

### 摘要區塊（檔案最上方，必須跟內文同步）

```markdown
## ⏳ 待確認（1）

- **D2** — <一句話說明卡在哪>
```

- 數字要等於內文 `⏳`／`🚫` 決策的數量
- 底下逐條列出，跟內文的決策編號要完全對得上（多列、少列、或列出已經是
  `✅` 的都算錯誤——這是最常忘記同步的地方）

## review.md

跟 `design.md` 幾乎一樣，只是欄位名稱換成審查情境，狀態只有兩種（沒有 `🚫`）：

### 已結案（✅）

```markdown
### ✅ F1 — <一句話結論>

- **位置**：<檔案路徑:行號>
- **問題**：<reviewer 發現了什麼>
- **處置**：<改了什麼，或為什麼不改>
```

`位置`／`問題`／`處置` 三個**全部必填**。

### 待處理（⏳）

```markdown
### ⏳ F2 — <還沒結案的問題>

- **位置**：<檔案路徑:行號>
- **問題**：<reviewer 發現了什麼>
- **選項**：
  - [ ] <候選處置方案一>
  - [ ] <候選處置方案二>
  - [ ] 其他補充：
```

同樣不能寫 `處置` 欄位，`選項` 規則跟 `design.md` 完全一樣。

摘要區塊標題是 `## 🔴 待處理（N）`（不是 `⏳ 待確認`）。

## 通用規則

- 嚴禁代碼塊標記（```）——狀態圖、程式碼片段這類內容不該塞在這裡
- D/F 編號在同一份檔案裡不能重複
- 每個欄位值不能超過 200 字元——逼你精簡，不是把一整段話塞成一行

## 寫完之後

跑 `specflow next <change-id> --spec-root <spec-root>`（或
`specflow transition ...`）。`gate_check` 只要偵測到這兩個檔案存在，就會自動
驗證；錯誤訊息會精確指出是哪個決策／發現、哪個欄位、什麼問題，照著訊息修，
不要憑猜測大改整份檔案。
