# MR Review → review.md

## 這個 skill 做什麼

specflow 本身完全不碰 GitLab/GitHub 的 MR/PR API——它只認本機檔案系統。這個
skill 是中間的橋接層：把一串自由格式的 review 討論，轉寫成 specflow 認得、
`review_lint` 驗證得了的結構化格式，落地成 `changes/<change-id>/review.md`。

## 目標格式

每個 review 發現是一個独立項目，用固定欄位、不準寫成自由段落：

```markdown
---
change: <change-id>
---

## 🔴 待處理（N）

- **F<n>** — <一句話說明卡在哪>

## Review 發現 (Findings)

### ✅ F1 — <一句話結論>

- **位置**：<檔案路徑:行號>
- **問題**：<reviewer 發現了什麼>
- **處置**：<改了什麼，或為什麼不改>

### ⏳ F2 — <還沒結案的問題>

- **位置**：<檔案路徑:行號>
- **問題**：<reviewer 發現了什麼>
- **選項**：
  - [ ] <候選處置方案一>
  - [ ] <候選處置方案二>
  - [ ] 其他補充：
```

規則（`review_lint` 會強制檢查，寫錯格式會被擋下）：

- **已結案（✅）**：只能用 `位置` / `問題` / `處置` 三個欄位，三個都必填，`處置`
  是自由文字一行，說清楚「改了什麼」或「為什麼不改」
- **待處理（⏳）**：只能用 `位置` / `問題` / `選項`，不能寫 `處置`——還沒結案就
  不該假裝已經有答案。`選項` 至少要有 2 個候選方案，且必須包含一項
  「其他補充：」，不能變成強迫二選一
- 檔案最上方的「🔴 待處理（N）」摘要，N 要等於內文 `⏳` 的數量，底下逐條列出
  `- **F<n>** — <一句話>`，這份摘要要跟內文同步，不能漏更新
- 嚴禁代碼塊標記（```）
- 每個項目的位置欄位優先抓原始留言裡明確寫出的「檔名:行號」，沒有就寫
  「（原始留言未指出明確位置）」，不要自己編

## 步驟

1. **取得 MR/PR 完整討論串**
   - 如果有 GitLab/GitHub connector 可用，用它抓這個 MR 的所有 thread（含每條
     的原始留言跟後續回覆），不要只抓摘要
   - 如果沒有 connector，使用者可能會直接貼上 MR 頁面的文字內容——把貼上的
     內容當成完整討論串處理，不要假裝去抓資料

2. **逐條 thread 判斷結案狀態**
   - reviewer 提出問題後，作者有沒有明確回覆「已修」「不修＋理由」？
     - 有 → `✅`，`處置` 欄位濻縮成一句話（不是逐字複製 commit message）
     - 沒有、或討論還在來回、或標記「之後再處理」→ `⏳`
   - **不要因為 thread 串很長就假設它已經結案**——沒看到明確的處置結果，
     一律標 `⏳`，寧可保守也不要漏掉真正還沒解決的問題

3. **問題欄位要精簡，不是逐字複製**
   - `問題` 欄位是 reviewer 論點的濻縮版，抓核心（「哪裡不對、為什麼不對」），
     不是把整段留言貼過去——那樣又會變回「自由段落」，違背這個格式存在的目的

4. **寫入 `changes/<change-id>/review.md`**

5. **驗證格式**：跑 `specflow next <change-id> --spec-root <spec-root>`（或
   `specflow lint` 系列指令，視專案而定）——如果 `review.md` 存在，
   `gate_check` 會自動驗證它，錯誤訊息裡會清楚說明具體是哪個欄位、哪個項目
   不合規，照著訊息修正，不要用猜的

6. **有 `⏳` 項目時，明確跟使用者說**：這個 MR 還有幾條沒結案的發現、分別是
   什麼，不要只回報「已經整理完成」

## 常見錯誤（自我檢查）

- 把一段落自由文字塞進 `處置` 或 `問題` 欄位，格式上會通過 lint 但違背這個
  格式存在的初衷——**盡量濻縮成一句話**，需要更多脆絡就拆成多個欄位或直接
  連結回原始 MR
- 忘記同步更新頂端的「🔴 待處理（N）」摘要
- 把明明還在討論、沒有明確結論的 thread 標成 `✅`——這是這個格式最重要的
  誠實承諾，寧可保守
